## 1. 模块定位

| 项 | 内容 |
|---|---|
| **职责** | 维护滑动时间窗口（**纯进程内**）→ 聚合 **18 项特征** → 产出并落库 `feature_snapshots`（含 `missing_features` 缺失标记） |
| **触发时机** | 每个事件进入决策链路时，在名单/规则判定**之前**执行 |
| **上游** | 03 事件接入网关（提供已校验的事件） |
| **下游** | 05 规则决策引擎（消费 `features` 做条件求值）；07/10 读取快照用于复核与仿真回放 |
| **对应 PRD** | 2.3.1「实时提取…多维特征快照」、**2.3.4 滑动窗口统计特征**、2.3.6「特征计算引擎」、2.3.8「特征上下文快照」 |
| **对应实体** | 写 **E02 `feature_snapshots`**；读 E01（滑窗输入）、E10~E13（画像类特征） |
| **对应原型** | `03_风控审核工作台.pen` 中栏「特征上下文快照（18 项，对比基线）」表；`05_事件仿真测试页.pen` 步骤 2 |
| **对应架构决策** | **AD-05**（进程内 `FeatureStore` 协议，可平滑替换 Redis） |

**本模块明确不做的事（见 `00_模块划分与边界.md` §3.3）**：
- **不碰规则**（不求值、不计分）——归 05
- **不碰名单**——归 05
- 不负责事件校验与幂等——归 03
- 不负责画像的**持久化聚合**（`users.stat` 等存量统计归 09）；本模块只做**窗口内**的实时特征

## 2. 页面结构

本模块无独占页面。其产出出现在**两处**，字段绑定如下。

### 2.1 展示点 A：`03_风控审核工作台` 中栏 · 特征上下文快照表 `snapTbl`

| 列 | 绑定字段 | 说明 |
|---|---|---|
| 特征名 | `features` 的键 | 展示 18 项中的**全部**（含未命中规则的） |
| 本次值 | `features[key]` | 布尔展示 `true/false`；比率展示百分比 1 位小数；计数展示整数 |
| 基线值 | **参照区间配置**（见 §4.5） | 如 `≤1`、`2~5`、`false`、`≤5%`、`—` |
| 偏离 | **前端派生**：本次值 vs 参照区间的方向与倍数 | 如 `▲ 12 倍`、`▼ 偏低`、`正常`；灰色表示无基线 |

**缺失特征处理**：`missing_features` 中的项，本次值列显示「数据不足」灰字，基线/偏离列显示 `—`。
**空态**：无快照时整表显示「无特征快照（数据异常）」，不显示空表格。

### 2.2 展示点 B：`05_事件仿真测试页` · 步骤 2「特征提取（18 项）」

| 元素 | 绑定 |
|---|---|
| 步骤标题 | `特征提取（18 项）` |
| 结论行 | `完成 · 耗时 {compute_ms}ms · 缺失 {len(missing_features)} 项` |
| 特征小表 | 展示 4~6 项**关键特征**（`device_user_cnt`、`coupon_cnt_1h`、`user_age_days`、`ip_is_proxy`），值取自 `features` |

**缺失数 > 0 时**配色改为橙色（提示冷启动）。

## 3. 接口字段

### 3.1 内部引擎接口（`FeatureStore` 协议，AD-05）

```python
class FeatureStore(Protocol):
    async def ingest(self, event: EventLite) -> None: ...
    async def compute(self, event: EventLite) -> dict[str, Any]: ...
    async def sweep(self) -> int: ...            # 清理过期数据，返回清理条数
    async def stats(self) -> dict[str, Any]: ...  # 供 /health 与系统设置展示
```

| 方法 | 语义 |
|---|---|
| `ingest` | 把事件写入各维度窗口。**必须幂等**：同一 `event_id` 重复写入不重复计数 |
| `compute` | 计算 18 项特征并返回 KV。**先 `ingest` 后 `compute`**（本事件计入窗口，见 BR-04-02） |
| `sweep` | 丢弃超出 `long_window` 的数据；由定时任务每 60s 调用 |
| `stats` | 返回各维度队列长度、总事件数、内存估算、最近 sweep 时间 |

### 3.2 `GET /api/v1/features/{event_id}` — 查询某事件的快照（供 07 / 10 读取）

**响应 `data`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `snapshot_id` | string | 快照编号 `SNP*` |
| `event_id` | string | 事件编号 |
| `user_id` | string | 冗余 |
| `features` | object | 18 项特征 KV |
| `window_config` | object | `{short_window_min, long_window_min, agg_mode, config_version}` |
| `computed_at` | long | 计算完成时间戳 |
| `compute_ms` | int | 计算耗时 |
| `missing_features` | array | 因数据不足未能计算的特征名 |

**状态码**：`200` / `404`（该事件无快照，`FEA-4004`）

### 3.3 `GET /api/v1/features/meta` — 特征元数据（供前端渲染表头与基线）

**响应 `data`**：`{ items: [{key, label, group, unit, data_type, baseline, baseline_desc}] }`

> **前端不得硬编码特征名与基线**（BR-04-16）——统一从此接口取，保证与后端一致。

### 3.4 对 05 的契约

05 通过内部调用 `store.compute(event)` 获得 `features`，**不通过 HTTP**（同进程内，避免额外开销）。
**契约冻结**：`features` 的键名与类型一经确定不得随意改名；新增特征需同步更新 `/features/meta` 与 Step1 的 E02 字段表。

## 4. 业务规则

### 4.1 窗口语义

| 编号 | 规则 |
|---|---|
| **BR-04-01** | 两个窗口：**短窗 60 分钟**、**长窗 1440 分钟（24h）**（对应悬空点 **G-02**，已按默认值确认） |
| **BR-04-02** | **先 `ingest` 再 `compute`**——当前事件**计入**窗口统计（即"近 1 小时同设备下单次数"包含本次）。理由：风控要拦截的是"这一次"，把本次排除会低估风险 |
| **BR-04-03** | 窗口边界为**左闭右开**：`[now - window, now)` 且含 `now` 这一笔（由 BR-04-02 保证） |
| **BR-04-04** | 时间以**事件时间 `ts`** 为准，不用服务器接收时间；但**乱序事件**（`ts` 早于已处理事件）需按 `ts` 插入正确位置，或标记为乱序并告警（见 §8） |
| **BR-04-05** | 窗口配置随快照一同落库（`window_config`），保证历史快照可用当时配置复算 |

### 4.2 十八项特征的定义与口径

**分组一 · 行为频次（7 项）**

| 特征 | 口径 |
|---|---|
| `login_cnt_1h` | 该用户近 1h 的 `login` 事件数 |
| `coupon_cnt_1h` | 该用户近 1h 的 `coupon_receive` 事件数 |
| `order_cnt_1h` | 该用户近 1h 的 `order_create` 事件数 |
| `order_cnt_24h` | 该用户近 24h 的 `order_create` 事件数 |
| `pay_fail_cnt_24h` | 该用户近 24h 的 `order_pay` 且失败的事件数 |
| `aftersale_cnt_24h` | 该用户近 24h 的 `after_sale_apply` 事件数 |
| `aftersale_rate_24h` | `aftersale_cnt_24h / max(order_cnt_24h, 1)`，保留 4 位小数；`order_cnt_24h = 0` 时该特征**标记缺失** |

**分组二 · 设备环境（3 项）**

| 特征 | 口径 |
|---|---|
| `device_user_cnt` | 该设备关联的**去重账号数**；**由模块 09 提供**（调用 `get_linked_user_count()`），本模块不自行维护，不限时间窗——团伙识别需要长期视角 |
| `device_order_cnt_1h` | 该设备近 1h 的 `order_create` 事件数 |
| `device_age_hours` | `(now - 设备首次出现时间) / 3600`；无记录时标记缺失 |

**分组三 · 网络 IP（3 项）**

| 特征 | 口径 |
|---|---|
| `ip_user_cnt` | 该 IP 关联的去重账号数（不限窗口，同设备口径） |
| `ip_order_cnt_1h` | 该 IP 近 1h 的 `order_create` 事件数 |
| `ip_is_proxy` | 布尔；由 IP 库的 `is_proxy`/`is_idc` 标记得出（E12） |

**分组四 · 地址聚集（2 项）**

| 特征 | 口径 |
|---|---|
| `address_user_cnt` | 该收货地址关联的去重账号数（不限窗口） |
| `address_aftersale_cnt` | 该地址的**历史售后申请总次数**（来自 E13.aftersale_cnt） |

**分组五 · 账号画像（3 项）**

| 特征 | 口径 |
|---|---|
| `user_age_days` | `(now - users.register_at) / 86400`，取整 |
| `user_level` | 取自 E10.`level` |
| `user_risk_tag_cnt` | `len(users.risk_tags)` |

| 编号 | 规则 |
|---|---|
| **BR-04-06** | **18 项特征的键名、口径、数据类型必须与本节完全一致**，并与 Step1 的 E02 字段表逐项对应；任一改动需同步三处（Step1 / 本节 / `/features/meta`） |
| **BR-04-07** | `device_user_cnt` / `ip_user_cnt` / `address_user_cnt` **一律向模块 09 取**（`get_linked_user_count()`，内部调用），**本模块不得自建去重集合**——同一指标只能有一个真源（对齐 09 的 BR-09-13/14） |
| **BR-04-08** | `aftersale_rate_24h` 在分母为 0 时**必须标记缺失**，不得返回 0（0 与"无法计算"语义不同，会误导规则判断） |

### 4.3 缺失特征

| 编号 | 规则 |
|---|---|
| **BR-04-09** | 无法计算的项必须写入 `missing_features`，**不得用 0 / null 冒充** |
| **BR-04-10** | 冷启动（新用户/新设备）时缺失项**允许较多**，但必须如实标记，供人工复核识别"数据不足"而非"表现正常" |
| **BR-04-11** | 缺失特征在条件树求值时的语义由 **05 的 BR-05-12** 定义（除 `exists` 外一律 `false`）——本模块只负责标记，不负责判定 |

### 4.4 容量与清理

| 编号 | 规则 |
|---|---|
| **BR-04-12** | 每个维度队列**上限 10000 条**（对应悬空点 **G-12**，已按默认值确认）；超出时丢弃最旧 |
| **BR-04-13** | 定时 sweep 每 **60 秒**执行一次，丢弃超出长窗的条目，并清理各维度空队列的键（`_linked` 归模块 09 维护，本模块不持有） |
| **BR-04-14** | sweep 必须**非阻塞**：不得长时间持有锁导致决策链路等待 |
| **BR-04-15** | `/health` 与系统设置页可查询内存占用估算；单进程内存超过阈值（如 500MB）时告警 |

### 4.5 基线（参照区间）——**跨步骤补漏**

> **发现的不一致**：`03_原型图` 的快照表有「基线值 / 偏离」两列（如 `≤1`、`2~5`、`false`、`≤5%`），
> 但 `01_数据实体` 的 E02 **没有存储基线的字段**。本节补齐该定义。

| 编号 | 规则 |
|---|---|
| **BR-04-16** | 基线是**静态参照区间**（每个特征一条），集中定义在 `feature_baselines.py`，并通过 `/features/meta` 下发；**前端不得硬编码** |
| **BR-04-17** | 基线**不参与决策计分**——计分只由 05 的条件树决定。基线仅用于**人工复核时的快速判读** |
| **BR-04-18** | 「偏离」列由**前端派生**（本次值 vs 参照区间），后端不计算、不下发文案 |
| **BR-04-19** | 无基线定义的特征（如 `user_age_days`）显示 `—`，不显示"正常"（避免误导为"已判定正常"） |

**基线配置示例**

| 特征 | baseline | 说明 |
|---|---|---|
| `device_user_cnt` | `≤1` | 一台设备正常只对应 1 个账号 |
| `coupon_cnt_1h` | `≤2` | 正常用户近 1h 领券不超过 2 张 |
| `ip_is_proxy` | `false` | 正常不应为代理出口 |
| `aftersale_rate_24h` | `≤5%` | 正常退款率上限 |
| `order_cnt_24h` | `2~5` | 正常下单频次区间 |
| `user_age_days` | `—` | 无绝对基线（新老用户都正常） |

### 4.6 并发与一致性

| 编号 | 规则 |
|---|---|
| **BR-04-20** | `FeatureStore` 在单事件循环内使用；对窗口队列等共享结构的修改需加 `asyncio.Lock` 或用单线程无锁结构（asyncio 单线程下同步修改是安全的，但**跨 `await` 的复合操作必须加锁**） |
| **BR-04-21** | `Snapshots` 与事件**分离存储**（Step1 原则 2）：事件不可变，快照可随特征定义演进而复算 |
| **BR-04-22** | 快照落库为**异步**（AD-01）；但决策链路**同步**需要 `features`，因此 `compute()` 必须就地返回，不等落库 |
| **BR-04-23** | 快照落库失败**不回滚决策**，转入重试队列并告警（最终一致） |

## 5. 异常处理

| 错误码 | 场景 | HTTP | 用户可见提示 | 处理 |
|---|---|---|---|---|
| `FEA-4001` | `event_id` 格式非法 | 422 | 「事件编号不合法」 | — |
| `FEA-4004` | 查询的快照不存在 | 404 | 「未找到该事件的特征快照」 | 07/10 页显示占位 |
| `FEA-5001` | 特征计算过程异常（如字段类型不符） | — | — | **降级**：`error` 字段置位，返回**可用特征子集** + `missing_features` 补充异常项；决策链路按 fail-closed 交人工审核 |
| `FEA-5002` | 快照落库失败 | — | 无（后台） | 入重试队列 + 告警；**不阻塞**同步决策返回 |
| `FEA-5003` | 窗口数据超容量被截断 | — | 中栏表格顶部黄条「部分窗口数据已截断，特征可能偏低」 | 记录告警；**必须提示**，不能静默 |
| `FEA-5004` | 检测到乱序事件 | — | 无（内部） | 按 `ts` 插入或丢弃并计数告警（见 §8） |

> **fail-closed 原则**：特征计算失败时**绝不返回"各项为 0"的假特征**——那会让规则全部不命中从而误判为低风险放行。
> 正确处理是：标记 `degraded` + 补 `missing_features`，并把决策默认引向**人工审核**。

## 6. 文件规划

```
├── engine/
│   ├── feature_store.py        # InMemoryFeatureStore：窗口结构、ingest、sweep、stats

├── tasks/
│   └── sweep_task.py           # 每 60s 的窗口清理定时任务（BR-04-13）
└── schemas/
    └── feature_schema.py       # 快照与元数据的响应模型
```

| 文件 | 职责 | 可单测 |
|---|---|---|
| `feature_store.py` | 窗口数据结构与生命周期 | ✔（注入假时钟） |

| `feature_baselines.py` | 基线配置 | ✔ |
| `feature_meta.py` | 特征元数据 | ✔ |

**测试重点**：`feature_calc.py` 必须覆盖 18 项特征各自的**正常 / 缺失 / 边界（分母 0、无记录）**三种情况。
